# Sidecar Deepening Opportunities

This note records architecture review candidates from applying the
`improve-codebase-architecture` skill to the Sidecar. These are not approved
implementation plans. They are candidate **deepening opportunities** to explore
one at a time.

Domain context:

- **Sidecar** owns agent turn execution, session management, tool dispatch,
  context management, LLM orchestration, provider auth, and the Shell RPC peer.
- **Agent Turn** is one user submission inside a session. It starts with
  `conversation.turnStarted`, streams `ui.*` notifications, mutates the
  **Conversation Transcript**, and ends as done, error, or cancelled.
- **Conversation Transcript** is the LLM-visible history owned by a session.

Architecture vocabulary:

- **Module**: anything with an interface and implementation.
- **Interface**: everything a caller must know to use the module correctly.
- **Implementation**: the code inside a module.
- **Depth**: leverage at the interface.
- **Seam**: where an interface lives.
- **Adapter**: a concrete thing satisfying an interface at a seam.
- **Leverage**: what callers get from depth.
- **Locality**: what maintainers get from depth.

## 1. Deepen Agent Turn Runtime

**Files**

- `sidecar/src/agent/loop.ts`
- `sidecar/src/agent/turn/tool-dispatch.ts`

**Problem**

`runTurn` is a high-leverage **Module**, but its **Interface** is shallow: one
function owns model/config resolution, compaction lifecycle, stream event
mapping, thinking close semantics, tool execution, UI notifications, provider
auth projection, Computer Use cleanup, steering, todo projection, and
cancellation repair. **Locality** is low because each lifecycle rule is
implemented inline across distant branches.

**Solution Direction**

Deepen around the **Agent Turn** lifecycle and round/tool execution **Seams** so
`loop.ts` orchestrates, while narrower **Implementations** own stream event
application, terminal state, and tool-round replayability.

**Benefits**

Tests can assert lifecycle transitions without booting full RPC/dispatcher
state for every case. Deletion test: removing the extracted round/lifecycle
logic would push stream, tool, cancellation, and terminal-state complexity back
into `loop.ts` and its callers.

## 2. Deepen Conversation Transcript Mutation

**Files**

- `sidecar/src/agent/conversation.ts`

**Problem**

`Conversation` is already a relatively deep **Module** for flat transcript
storage, but its public mutation **Interface** is still a collection of low-level
methods. Callers know too much about ordering: append assistant, record usage,
append tool results, finalize cancellation, mark done, compact. The
**Implementation** preserves important invariants, but the **Seam** is still too
close to array/range operations.

**Solution Direction**

Raise the **Interface** toward Conversation Transcript domain operations such as
turn slice transitions, replayability repair, and compaction application, while
keeping flat storage hidden.

**Benefits**

Fewer tests need to construct fragile message ranges manually. If `_messages`
and range storage were replaced, most Agent Turn tests should survive because
they would test behavior through the Conversation Transcript **Interface**.

## 3. Separate Tool Execution Adapter From Turn State Effects

**Files**

- `sidecar/src/agent/loop.ts`
- `sidecar/src/agent/turn/tool-dispatch.ts`
- `sidecar/src/agent/session/session.ts`

**Problem**

Tool dispatch has a promising **Adapter** in `tool-dispatch.ts`, but the Agent
Turn loop still owns side effects of specific tools: `start_app_session` and
`stop_app_session` mutate session Computer Use state by name. That leaks one
tool family's **Implementation** details into the generic Agent Turn runtime.

**Solution Direction**

Deepen the tool execution result/application **Seam** so tool-specific session
effects are applied near the tool **Adapter**, not by string matching in the
loop.

**Benefits**

Computer Use App Session lifecycle can be tested without synthetic full
assistant/tool rounds. Deletion test: deleting Computer Use tools should not
require editing generic tool loop logic.

## 4. Deepen Computer Use Tool Module

**Files**

- `sidecar/src/agent/tools/computer-use.ts`
- `sidecar/src/agent/session/computer-use-state-cache.ts`

**Problem**

`computer-use.ts` mixes several concerns in one **Module**: LLM tool catalog
text/schema, Shell RPC **Adapter** calls, argument validation, result rendering,
and screenshot coordinate state. Understanding Computer Use behavior requires
jumping between tool definitions, session state, cache behavior, and Agent Turn
post-tool effects.

**Solution Direction**

Keep the external registration surface stable, but introduce clearer internal
**Seams** around catalog/spec definitions, Shell RPC **Adapter** behavior, event
validation, result rendering, and coordinate state.

**Benefits**

Validation and rendering can be tested as focused in-process behavior. RPC
behavior can be tested with a fake dispatcher. Computer Use state changes gain
better **Locality**.

## 5. Move Wire Projection Out Of Core Runtime State

**Files**

- `sidecar/src/agent/session/session.ts`
- `sidecar/src/agent/conversation.ts`
- `sidecar/src/agent/session/handlers.ts`
- `sidecar/src/rpc/rpc-types.ts`

**Problem**

Core runtime **Modules** project directly to wire shapes through
`Session.toListItem()` and `Conversation.toWire()`. This is convenient, but it
weakens the **Seam** between Sidecar runtime state and RPC schema evolution.

**Solution Direction**

Move runtime-to-wire projection into an RPC **Adapter** layer so `Session` and
`Conversation` remain focused on runtime state, while RPC handlers own
serialization.

**Benefits**

Core state tests stop depending on wire field names. RPC conformance tests cover
projection explicitly. Changing Shell snapshot fields should not require
changing Conversation Transcript storage.

## 6. Deepen RPC Method Catalog Around Method Semantics

**Files**

- `sidecar/src/rpc/rpc-types.ts`
- `sidecar/src/rpc/method-catalog.ts`
- `sidecar/src/rpc/dispatcher.ts`

**Problem**

RPC method identity, direction, request/notification kind, timeout, and
fast-path metadata are split across constants and separate maps. The dispatcher
benefits from the current catalog, but the catalog **Interface** is still
shallow because method metadata can drift when a method is added.

**Solution Direction**

Make RPC Method Catalog a deeper local source of routing truth while leaving
schema types in `rpc-types.ts` per the existing Sidecar/Shell schema design.

**Benefits**

One table-driven test can prove every RPC method has required routing metadata.
Deletion test: adding or removing a method should fail one focused catalog test,
not multiple dispatcher tests.

## 7. Consolidate File Tool Path Policy

**Files**

- `sidecar/src/agent/tools/read.ts`
- `sidecar/src/agent/tools/write.ts`
- `sidecar/src/agent/tools/update.ts`

**Problem**

File tools repeat path resolution and policy. This is a small but clear shallow
**Implementation** duplication: future changes to `~`, relative path, or
absolute path semantics would scatter across multiple **Modules**.

**Solution Direction**

Deepen a file-tool support **Module** around path normalization and shared
file-tool policy. Keep business rules fail-fast and do not introduce fallback
logic.

**Benefits**

One test surface can cover `~`, relative paths, and absolute paths. Adding a new
file tool should not copy path handling.
